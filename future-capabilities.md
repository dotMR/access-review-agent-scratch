# Future Capabilities

Reasoning-capability candidates surfaced during design but not built for this project's current scope — genuinely developed sketches (the naive-version rejection, why each clears the "does this need AI, not just automation" bar, a concrete artifact shape), not just names on a list. Each stays here until (if ever) picked up as real scope, at which point it moves into `iam-review-agent-design.md` and `SPEC.md` proper. None of these are scheduled; nothing in `development-plan.md` commits to building any of them.

For the mechanisms that *are* built but not fully activated (Dormant admin-level's, Dormant ad-hoc's, and Drift's own Operational/SLA-bearing cadence; the grant-time Unapproved gate; contractor end-date expiry detection) — see `SPEC.md` §8's "Out of scope" list instead. Those are smaller, tightly coupled to existing categories, and don't need the depth of treatment below.

## Predictive prioritization: forward-looking, not just retrospective

Same stress-test as Identity resolution: does the project's thesis need AI, or just automation, when it comes to helping the Reviewer ahead of the audit rather than only reporting after it closes? Two versions considered, only one holds up:

- **Early-warning thresholds don't count.** Flagging dormant access at 60 days as "approaching" instead of waiting for the 90-day finding is just a second, earlier deterministic rule, no reasoning involved. Same for general access-footprint anomaly detection, that's the established UEBA/statistical-baseline discipline, not something that needs an LLM either. Neither moves the needle on the thesis.
- **Remediation-velocity synthesis does.** The agent already tracks every open finding as a GitHub Issue and already reasons retrospectively about Unremediated findings (did this stay open past the cycle boundary). The predictive version runs the same reasoning forward: given how a specific Asset Owner, system, or finding category has historically behaved (most dormant findings close within two weeks; this one's been open 45 days with no activity), plus whatever context exists on the Issue itself, surface "this is trending toward still being open at audit time" ahead of the formal report, not just after it. Weighing historical velocity against current state is reasoning, not a threshold comparison.

**Same engine, forward-facing.** Not a fourth mechanism alongside Identity resolution, it's the same reasoning-over-evidence capability pointed at a different question: not "who does this access belong to" but "is this specific open finding on track to be remediated before the next cycle, or not." Same restraint property both times, citing what the prediction is based on (X findings of this category historically closed within Y days) rather than asserting confidence with no traceable basis.

**Status: out of scope for this build.** Depends on having enough closed-Issue history to compute real remediation-velocity baselines, which `demo-timeline.md`'s three simulated quarters don't generate enough of; a real deployment would accumulate this from actual operating history.

## Certification-triage by novelty (thin note, not developed)

A candidate surfaced during the AI-in-compliance research pass, thinner than the other cases in this file, logged so it isn't lost rather than as a developed case. Distinct from Predictive prioritization: that asks whether a specific open finding will still be unresolved by audit time, a forecast. This asks something else, of everything flagged this cycle, which findings actually warrant the Reviewer's limited attention versus which are recurring, already-understood patterns, a novelty judgment, not a severity ranking. Real IGA practice does something like this ("AI can surface only high-risk entitlements for review and automate low-risk certification decisions," see ai-in-compliance-research.md). Same discipline as the other cases: a naive version, fixed severity ranking, is deterministic and not AI-necessary; what would be load-bearing is comparing a new finding's context against the pattern of prior findings and decisions to judge genuine novelty. Not sketched further, no artifact shape proposed yet.

**Status: out of scope for this build**, and less developed than the other candidates here.

## Policy-to-config drift detection: same engine, self-directed

Same stress-test as the other cases: does verifying that `policy-config.yaml` and `role-access-mapping.yaml` still faithfully reflect `access-control-policy.md`'s prose need AI, or is a diff enough? Surfaced from an accepted risk `iam-review-agent-design.md` already names twice — the original policy/config split ("the two can drift out of alignment if one changes without the other being updated to match, judged acceptable... not worth the build effort," Data and config formats) and ADR-0004's identical acceptance for `role-access-mapping.yaml`. Both were the right call when made, before a reasoning engine existed that could check them cheaply.

- **A literal diff or checksum doesn't count.** "Did any of these files change" fires on every legitimate edit, not just ones that introduce a mismatch — pure noise, no judgment of meaning, the same category of naive-and-rejected as Predictive prioritization's early-warning thresholds.
- **Semantic comparison does.** Confirming that `access-control-policy.md`'s "dormant and unused for more than 90 consecutive days" (the Dormant Admin-level access Principle) still matches `policy-config.yaml`'s `admin_level_days: 90` isn't a string match — the prose doesn't share a common key or format with the config value the way an `employee_id` does with an access record. It's reading comprehension against a specific structured value: which Principle, which config key, do they still agree, and citing both rather than asserting a verdict with no traceable basis. The same restraint property Identity resolution already has: decline to assert drift when a mapping is genuinely ambiguous (a reworded Principle whose intent isn't obviously the same or different) rather than guessing either way.

**Same engine, self-directed.** Not a new mechanism, the same reasoning-over-evidence capability already built for Identity resolution and sketched for Predictive prioritization above, pointed at a new kind of question: not "who does this access belong to" or "will this finding still be open at audit time," but "is the agent's own configuration still faithful to the policy it's enforcing." Same citation discipline, same restraint.

**Scope is narrower than it first sounds.** This works cleanly for the *parametric* Principles — the ones with a literal number or trigger stated in prose (Dormant Admin-level's 90 days, Dormant Ad-hoc's 180 days, Orphaned's same-day SLA) each map to exactly one `policy-config.yaml` value. It doesn't naturally extend to `role-access-mapping.yaml`'s Role → Access table against the Role-based Access Principle — that Principle is a process requirement ("access must be granted according to role"), not a specific value, so there's nothing concrete in the prose to compare each table row against. Checking whether the table itself still reflects least privilege would be a genuinely harder, more subjective judgment, out of scope here too.

**Concrete shape, sketched not built.** Not a Finding in `CONTEXT.md`'s sense — this isn't a discrepancy in a person's access, it's a discrepancy between the agent's own inputs. Follows the same "synthesis, not a Finding, but still needs a human-facing artifact" pattern already established for Risk Assessment Entries: no per-item GitHub Issue, but a labeled Issue (e.g. `policy-config-review`) for genuinely flagged mismatches, reusing the CAPA-style process-level labeling already sketched for Risk assessment's systemic treatment recommendations rather than inventing a new mechanism.

**Status: out of scope for this build**, cheaper than the other candidates here — no new architecture, no new tool, reuses the reasoning engine built for Identity resolution nearly as-is. Directly resolves two risks `iam-review-agent-design.md` already names as accepted rather than solved, rather than opening a new one.
