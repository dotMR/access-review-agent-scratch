# Demo Timeline

A minimal, concrete sequence of data events, across three simulated quarters, that exercises every v1 Core capability at least once: six finding types (see `SPEC.md` §4 and §8 for the current list and scope), the Risk Assessment section synthesized across all of them, Orphaned's Operational and Evidentiary variants (the one finding type with a live event-triggered/quarterly pairing in v1 Core, see the note below), a live Escalation to the Reviewer, remediation closing the loop, the accepted-risk path, a real trend line by Q2, and the monthly summary catching a finding no push-triggered run would have (see the note below). Companion to `iam-review-agent-design.md`, both its Demo use cases section (the finding types themselves) and the rest of the doc (why each of these decisions was made).

This is what the seeding/scenario-generation tool (see iam-review-agent-design.md, "Demo timeline") should produce. Git commits and tags get their real dates, whenever they're actually made, the quarters below are simulated business periods labeled explicitly in the data and reports, not backdated history. Findings should be spread across at least a couple of different Information Systems, not concentrated on one, so the per-system reports have varied content to demonstrate the split meaningfully — this version touches all five Information Systems, not just three.

Guardrail proof (the grounding-check catching a fabricated finding, input-safety resisting an injected instruction) does not belong in this timeline, it lives in the eval fixtures (see iam-review-agent-design.md, Evals). Mixing a deliberately fake record into this data would undermine its credibility as a plausible business dataset.

**No monthly Operational/SLA tier in v1.** Dormant admin-level's, Dormant ad-hoc's, and Drift's own Operational/monthly, escalation-eligible variants are out of scope for this build — a deliberate product boundary (Escalation reserved for genuinely acute risk, per Orphaned), not a cost cut. Every Core finding type is either event-triggered (Orphaned) or Evidentiary/quarterly-only for *notification* purposes. The risk-based-cadence story survives in a thinner form: acute risk (Orphaned) still gets immediate treatment, everything else still waits for the quarterly cycle to become a formal, SLA-bearing record — though detection itself runs monthly too, not just quarterly, closing a gap where a quiet system could otherwise go unchecked (ADR-0003). This timeline's GitHub thread (commits 3 and the mid-Q2 monthly beat, below) is that gap made concrete: a system with no commits of its own for a full quarter still gets caught within a month of crossing the dormant threshold, not up to a full quarter later.

## Pre-Q1 / Day 0

- **Commit 1 — Seed baseline.** Several employees across roles with clean baseline access per role-access-mapping.yaml, plus one deliberately pre-aged record already past threshold: admin-level access on Finance ERP, idle since well before day 0 (Finance ERP chosen deliberately, it's rated Critical in role-access-mapping.yaml's System Criticality table, which is what lets this record anchor the Risk Assessment systemic-pattern example once it persists across quarters, see iam-review-agent-design.md, Data requirements). Sets up Dormant admin-level access without needing to wait out real quarters.
- **Commit 2 — Seed a pre-aged Dormant ad-hoc access record (Salesforce).** Engineering Manager Sleve McDichael's ad-hoc Salesforce read access (their baseline is none — approved individually by Salesforce's Asset Owner for a cross-functional project), idle since well before day 0, already past the 180-day threshold. Salesforce chosen for spread (High-criticality, untouched by any other commit in this timeline until now) and because it's a genuinely different scenario from Commit 1: ad-hoc/non-baseline access going stale, not an admin-level grant.
- **Commit 3 — Seed a GitHub admin-level grant, currently compliant.** Engineering Manager Bobson Dugnutt's baseline GitHub access (admin, per role-access-mapping.yaml — legitimate, no ad-hoc approval needed), recently used as of day 0. No finding yet: this is the setup half of the quiet-system scenario, not a seeded violation. No further GitHub commits occur until Q3, so nothing re-triggers detection for this system on its own — only the monthly trigger's own cadence will (see the Q2 note below).
- **Commit 4 — Seed a clean Identity resolution case (stale-ownership case, happy path).** A CI/CD service account access record with a provisioning note naming an accountable human owner, currently active in HR. Resolves cleanly to a documented non-individual exception, no finding, proving Identity resolution isn't just anti-join-and-flag. Confirm at build time that the audit report correctly omits this record from findings, this is the record commit 14 later reactivates.
- **Commit 5 — Seed an SSO-gap Identity resolution case (name-similarity, happy path).** A VPN access record with a local identifier (e.g. `kjack_vpn`) that doesn't match any HR `employee_id`, `provisioning_note`: "VPN access requested by K. Jack, IT ticket #4821." Resolves via name/email similarity against HRIS's `name` field to one plausible active match (Kelly Jack), a documented individual, no finding. A genuinely different reasoning path from commit 4, fuzzy name-matching against structured HR data rather than extracting and re-validating a named owner from prose over time, so the two clean-resolution seeds together prove the engine handles both of Identity resolution's non-violation cases, not just one.

## Q1 2026

- **Commit 6 — Hire.** Willie Dustice joins, baseline access auto-granted (`approved_by` = "auto..."). Clean event, no finding, proves the happy path works too.
- **Commit 7 — Ad-hoc access, unapproved (AWS, write-level).** Access granted on AWS for Mike Truk, a High-criticality system per role-access-mapping.yaml, with `approved_by` left null. Sets up Unapproved access; this is the instance that persists into Q2 as a genuine recurring signal (see commit 10's isolated, low-criticality counterpart, added deliberately as its contrast).
- **Commit 8 — Identity resolution, unresolved case.** A leftover access record whose `employee_id` matches no HR record, with no provisioning note or justification of any kind. Insufficient evidence to resolve to an individual or a documented exception, correctly resolves to unresolved rather than a guess, and is flagged — deliberately left unnamed, since there's no evidence to resolve an identity from. Sets up Identity resolution's Q1 audit finding. Opens as Issue #8, "Identity resolution — {{identifier}} (VPN)."
- **Commit 9 — Termination.** Ronnis Pawgood leaves; access not yet revoked. Sets up Orphaned access. The same-day event-triggered notice (Agent → Asset Owner, urgent) fires on the next run, independent of the quarterly cycle. Opens as Issue #9, "Orphaned access — Ronnis Pawgood (AWS)."
- **SLA missed, escalation fires.** The access from commit 9 isn't revoked the same day. The next time the agent runs, it re-checks Orphaned's same-day SLA (see iam-review-agent-design.md, Closing the loop), finds it missed, and escalates: Issue #9 gets the `escalated` label added and a comment posted stating the SLA was missed and when, per access-control-policy.md's Unremediated findings Principle, well within Q1, not at a quarter boundary. No assignee — see SPEC.md §4, Escalation mechanism. This is the timeline's one live Escalation moment, demonstrating a domain concept, Escalation, that until its promotion had nothing in v1 actually exercising it, and it's checked against Orphaned's own Operational cadence, the only category in v1 Core with one, not the quarterly cycle. AWS's monthly report, whenever it next runs before commit 12's remediation, shows Issue #9 too — still open, already escalated — proving the monthly report's "every currently open finding, no category exclusion" scope in practice, not just in the spec.

**End of Q1 — quarterly audit runs.** Five categories now have at least one finding: Orphaned, Dormant admin-level, Dormant ad-hoc, Unapproved, Identity resolution (Drift's first opportunity to appear is Q2, see commit 11 below; GitHub's Dormant admin-level thread hasn't crossed its threshold yet, see the Q2 note). Orphaned's entry shows *still open, already escalated*, the SLA was missed and escalation already fired mid-quarter, this is a confirmation in the formal record, not a new event at audit time. Five Issues opened, one per finding. Commits 4 and 5's clean resolutions correctly generate no Issues. Risk Assessment section appears for the first time: one score + narrative per category with a finding this quarter, no trend/pattern language yet, there's no prior audit to compare against, same reasoning as the trend line reading "N/A, no prior period." One escalation this period, already recorded above, section not empty this time. Release tagged `2026-Q1` and published behind the human-in-the-loop gate.

## Q2 2026

- **Commit 10 — Isolated, low-risk Unapproved access (VPN), flagged and remediated within the same quarter.** A separate, one-off ad-hoc VPN grant for Todd Bonzalez, read-level, non-admin, `approved_by` left null; the Asset Owner corrects the missing approval before Q2's audit runs. VPN is rated Low in role-access-mapping.yaml's System Criticality table, and this instance never carries into a second audit. This is the dedicated Risk Assessment contrast case: Likelihood = Low (new and already closed within this one audit), Impact = Low (VPN, read-level) → Risk rating: Low, sitting in the same Q2 report right next to Dormant admin-level and commit 7's Unapproved instance, both flagged as recurring on higher-criticality systems.
- **Commit 11 — Role change (mover).** Karl Dandleton changes roles; access doesn't yet follow. Feeds Drift-Evidentiary, v1 Core, first shows up in this quarter's audit. Drift-Operational (the monthly notice) is out of scope for this build, so this mismatch is caught quarterly, not immediately.
- **Commit 12 — Remediation.** Asset Owner revokes the Q1 orphaned access, acting alone: Orphaned itself never independently re-escalates (Unremediated findings already fired once, back in Q1), so the Reviewer's own involvement here was via that earlier escalation, not this remediation act. Issue #9 closes automatically on the next run — the re-check finds the access is actually gone.
- **Commit 13 — Accepted risk.** The Reviewer investigates the Q1 unresolved Identity resolution finding (commit 8) by hand and determines it's actually a legitimate documented shared account, evidence that existed outside the system and wasn't available to the agent, then labels Issue #8 `accepted-risk` rather than remediated — which closes the Issue, the same action as remediation, distinguished only by the label persisting as the permanent record of why (see CONTEXT.md, Accepted Risk). This is the payoff of the engine's restraint: it correctly declined to guess in Q1 rather than wrongly asserting either a violation or a clean resolution, and a human closes the loop with context the agent didn't have.
- **Monthly report catches GitHub's dormant admin access, mid-Q2.** Commit 3's grant crosses 90 days unused with no GitHub commit having occurred since day 0 — nothing push-triggered would have caught this. That month's monthly cron trigger runs full detection anyway (ADR-0003), finds it, opens Issue #{{n}} ("Dormant admin-level access — Bobson Dugnutt (GitHub)"), and it appears on that month's GitHub `reports/monthly/2026-05/github.md` — weeks before Q2's quarterly audit would have found it regardless. This is the proof-of-fix moment for the gap that motivated ADR-0003's revision.

**End of Q2 — quarterly audit runs.** Six categories now represented: Drift appears for the first time (from commit 11), and Dormant admin-level now spans two systems — Finance ERP (2nd consecutive quarter) and GitHub (new this quarter, first surfaced by the monthly report above, now formally in the quarterly record too). Status spread across every state on purpose: Orphaned remediated, Identity resolution accepted-risk, Unapproved and Dormant admin-level (both systems) and Dormant ad-hoc still open, Drift newly flagged and open, plus commit 10's isolated Unapproved instance, already remediated within this same quarter. No new escalation this period, Q1's already fired and its finding is now remediated via commit 12, quarterly-only categories have no Operational cadence to escalate against regardless of how long they stay open, that's Risk Assessment's job, not Escalation's. First real trend line, comparing against Q1. Risk Assessment narrative can now show a genuinely varied picture in one report: Finance ERP's Dormant admin-level (Critical criticality → High Impact) recurring for a 2nd quarter next to GitHub's brand-new instance of the *same category* (Medium criticality → Medium Impact) — same finding type, two systems, two different Impact ratings from ADR-0002's table, not just a recurring-vs-isolated contrast but a criticality-vs-criticality one; commit 7's AWS Unapproved instance, still open, recurring; and commit 10's VPN instance, flagged once and already closed, the clean isolated contrast the section needs. Release tagged `2026-Q2`.

## Q3 2026

- **Commit 14 — Second termination, doubling as the sharpest Identity resolution case.** The departing employee is also the documented owner of the Day-0 service account (commit 4). This single event produces two findings on the next run: a fresh Orphaned instance, their own access, revoked within the same-day SLA this time, a deliberate contrast with Q1's miss and escalation, no Escalation fires here; and a newly-stale service-account-ownership finding, Identity resolution re-validates the owner's current HR status on every run and catches that the accountability linkage has gone stale, the sharpest of Identity resolution's three cases (see iam-review-agent-design.md) and invisible to every other v1 Core check, since the service account's own identifier never matched an HR record to begin with. One event, two genuinely different outcomes: an SLA met cleanly, and a reasoning failure caught that no other check could see.

**End of Q3 — quarterly audit runs.** Trend line continues. Dormant admin-level (both systems), Dormant ad-hoc, Unapproved, and Drift findings persist (still unresolved, realistically, nothing in this timeline addresses them). Finance ERP's Dormant admin-level and commit 7's AWS Unapproved instance both hit a third consecutive quarter — the strongest recurring examples in the timeline, Likelihood = High for both, but different Impact (Finance ERP: Critical criticality × admin-level → High; AWS: High criticality × write-level → Medium), so Finance ERP's Risk Rating reaches Critical while AWS's reaches High — the timeline's fourth and last distinct Risk Rating value, completing the full Low/Medium/High/Critical range across the three quarters. GitHub's Dormant admin-level, by contrast, is only in its second consecutive quarter here — Likelihood = Medium, the same category (as Finance ERP) caught mid-stream at two different points, showing the Risk Assessment's recurrence scoring actually discriminating by history, not just by category. Remediation history shows two different SLA outcomes side by side (Q1's missed SLA and escalation vs. Q3's clean same-day close). No escalation this period, the Q3 Orphaned instance meets its SLA. Release tagged `2026-Q3`.

Three quarters covers detection, Identity resolution's two clean-resolution paths plus its unresolved fallback, and a live escalation fired mid-quarter off Orphaned's own SLA, not a quarter boundary (Q1); remediation, trend, accepted-risk (with the Issue-closing mechanics made explicit), the monthly report catching a finding no commit-triggered run could have, and Risk Assessment's first systemic-vs-isolated contrast plus a same-category, two-system Impact contrast (Q2); and recurrence at two different points in the same category, plus Identity resolution's sharpest case, this time with the SLA met and no escalation (Q3). Risk Assessment synthesis matures alongside the trend line: no pattern language in Q1, a recurring flag, a clean isolated contrast, and a criticality-driven Impact contrast by Q2, two different recurrence depths in the same category plus the full Low/Medium/High/Critical Risk Rating range by Q3. All five Information Systems are touched at least once. A fourth quarter would repeat the pattern rather than add a new capability, not needed for a minimal demonstration.
